## 2. Engine / runtime model (threads, time, ordering, randomness)

- [OBSERVED] The game's Lua 5.2.2 seeds its string hash with the clock and memory addresses, so table traversal order (`pairs`) of string-keyed tables differs on every PC/run. The game's own scripts (towns, industries, constructions) walk tables in that order and take different decisions; the author found this to be the main cause of desyncs (0.3.4; CL:400-407; RM:82-84; RD:21-22; DS:23). Consequence for us: any analysis that depends on iteration order of Lua tables from the game is non-deterministic between runs; sort by id/name before export. | high | engine.md, snapshot_schema.md (stable ordering) | NEW
- [OBSERVED] After seeding Lua identically, two untouched games stayed identical for 18 min of game time (before: diverged after 6 min), 10-min session at x4 stays identical (0.3.4; CL:405-407). Implies the engine simulation itself is deterministic given same inputs and ordering. | med | engine.md | NEW
- [OBSERVED] On CPUs with >= 8 threads the engine updates the game scripts (towns, loans, industries...) in parallel, in an order depending on thread timing; on smaller CPUs it uses a single worker. This caused a slow simulation drift (0.1.1; CL:697-703). Simulation, rendering, loading keep all cores. | med | engine.md | NEW
- [OBSERVED] Game random numbers of the mechanics (loan offers, contracts/subsidies, events, weather, industry events) are produced by the engine and identical for identical inputs; MPFever had to synchronise their seeds (0.1.1; CL:681-683, CL:721-722). So loan offers, subsidies, weather events are random draws, not functions of time alone. | high | engine.md, mechanics.md M7 (loan offers random draw) | CONFIRMS-EXISTING (mechanics.md M7: "randomly generated" offers)
- [CODE] The simulation's seeds for the vehicle shuffle (which vehicle reserves track first), the vehicle variant pick, and town and street development are taken from `GameTime.tickCount` (0.3.14; CL:95-99). `tickCount` also counts frames during which the game stands still (a game paused / waiting), so it differs between games; TPF3-MP's "paused-tick" fix is not counting them. Hence game time ticks (`tickCount`) are NOT a pure simulation-step count. | high (time axis of snapshots: do not equate tickCount with simulated steps) | engine.md, snapshot_schema.md | NEW (snapshot_schema notes raw ticks are internal but not this)
- [CODE] The engine's simulation works in "steps"; a "step count" separate from `tickCount` exists and is the proper measure of simulated time (0.3.14; CL:95-99). | med | engine.md | NEW
- [CODE] The engine's game-time component has an update counter that proves the engine is still (not stepping): used instead of a time check (0.3.11 PR #40; CL:198-201). Paused game: time does not advance, but scripts still run. | med | engine.md | NEW
