## 1. Builds, executable identity, signature approach

- [CODE] Two builds are known to the native module: 40408 (PE link timestamp 0x6ab69fe5) and 40420 (0x6ac50427). The "build number" is a label the author attached to a PE `TimeDateStamp`; the launcher derives it by reading the PE header of TransportFever3.exe (offset 0x3c -> PE header, +8 = timestamp). Unknown stamp => reported as "unknown build" (native/mpfever_native.cpp:20,350-351; launcher/Reporter.cs:121-138; tools/targets_40420.txt:1-2). Relevance H (our `meta.buildVersion` can be cross-checked against the PE stamp). Home: engine.md (builds) + snapshot_schema.md note. NEW. Build 40408 and 40420 are both marked.
- [CODE] No FileVersion/ProductVersion resource of the exe is read anywhere in the slice; build identity is solely the PE link timestamp (Reporter.cs:121-138). Relevance M. Home: troubleshooting/docs. NEW. Executable version string: NOT FOUND in slice (see Open questions).
- [CLAIM] Addresses (RVAs of TransportFever3.exe) "change with every game update", so the native module checks bytes before patching (RESEARCH.md:5). Relevance L. Home: engine.md appendix note. NEW.
- [CODE] Between 40408 and 40420 the same functions exist at shifted RVAs with the same internal offsets (UI tool call sites differ by a constant-ish delta, e.g. Bulldozer::Apply 0x4d45af -> 0x4d396f); "found again with the call graph" (native/mpfever_native.cpp:314-338). Relevance L. Home: engine.md (build-stability).
- [CODE] Signature approach: tools/mksigs.py builds, from a disassembly of the executable's .text, the shortest byte signature (12-128 bytes, up to 12 instructions of leading context) that matches exactly once; bytes that change between builds are wildcarded: RIP-relative displacements, 32-bit call/jump distances, 8-byte movabs address immediates (tools/mksigs.py:1-15,22-24,46-58). On a build it does not know, the native module uses these signatures; a feature turns on only if ALL its places match once (fail closed) (native/mpfever_native.cpp:1929-1936,2100-2102). Relevance L (technique), M for "which places are stable across builds". Home: engine.md (appendix on build-resilience).
- [CODE] Structure offsets inside engine objects (game-state +0x20C etc.) are still those of build 40420 even when addresses come from signatures (docs/CHANGELOG.txt, "structure offsets ... are still those of build 40420"; native/mpfever_native.cpp:2086,2100-2102). Relevance L.
- [CODE] Per-build places list (RVAs, build 40420) is in the Appendix. Build 40408's table is at native/mpfever_native.cpp:315-326,350.
- [CODE] The module is built as `winhttp.dll` (freestanding C++, no CRT, MSVC 2022+ toolset; `__chkstk` supplied separately because recent toolsets call it and there is no CRT) (native/build.bat:2-23; native/chkstk.asm; native/win.h:1-2). Relevance L. Home: skip (installer-level).
- [CODE] The game imports WINHTTP.dll (14 functions: Open, Connect, OpenRequest, SetOption, ReadData, SetStatusCallback, CloseHandle, WriteData, QueryDataAvailable, SetTimeouts, QueryHeaders, AddRequestHeaders, SendRequest, ReceiveResponse) and Windows searches the game folder first, so a same-name DLL there is loaded by the game at startup (native/winhttp_proxy.cpp:1-6,38-51). Game-fact value: the engine uses WinHTTP (online/telemetry-type HTTP) via those 14 calls. Relevance L. Home: engine.md (imports). NEW. [CODE] A launcher check treats a pre-existing winhttp.dll in the game folder that does not contain the string "mpfever_native" as "another mod" (Core.cs:1208-1216).
- [CODE] The game is loaded in-process on its main (interface) thread: `DllMain` runs on that thread, which the module records as the main thread id (native/mpfever_native.cpp:3214). Relevance L.

## 2. Threads, timing, step length

- [CODE] Main thread: `CGame::Sync` runs "every 200 ms, whatever the game speed"; it swaps the command list so that commands queued by the interface reach the simulation only at that swap (RESEARCH.md:31). Relevance M. Home: engine.md (time model). NEW.
- [CODE] Contradiction-in-source (author-internal): native comment says Sync is called every `guiFrameTime` microseconds, "set by Sync from the engine's own estimate, 200-400 ms", each call hands the simulation thread its next BATCH of updates: "one update at 1x, four at 4x", the renderer interpolating across the batch (native/mpfever_native.cpp:2828-2831). So the 200 ms is the nominal step; the real-time batch interval varies 200-400 ms. Relevance M. Home: engine.md. NEW. Mark: RESEARCH.md:31 vs native:2828 differ in precision (fixed 200 ms vs 200-400 ms estimate).
- [CODE] `guiFrameTime` is an i32 at offset +0x218 of the object at `CGame+0x1f0` (m_data); plausible values are accepted only in 20,000..2,000,000 (microseconds; i.e. 20 ms..2 s) and two i64 counters sit at m_data+0x1a0/+0x1a8 (native/mpfever_native.cpp:2828-2888). [ASSUMED] unit is microseconds because the comment says "every guiFrameTime microseconds". Build 40420 layout. Relevance L.

## 3. Command kinds and the command pipeline

- [CODE] Commands carry a kind byte; the native module reads it as the byte at payload+0x9b8 ("the dispatcher's index"). Known kinds: 52 = WorldBuildProposal (every construction tool), 42 = VehicleBuy, 57 = PerformSimulationSteps, 27 = ScriptingSendEvent (RESEARCH.md:33-38; native/mpfever_native.cpp:872-874,1459-1462). Relevance M. Home: engine.md (command kinds), api_catalog.md. NEW.
- [CODE] Kind 52 also covers PREVIEWS; those are applied "directly" outside the simulation loop (RESEARCH.md:39; native/mpfever_native.cpp:1355,1368-1369: "the other callers apply one command at once ... a preview ... applied directly, never by the loop"). Relevance M. Home: engine.md. NEW.
- [CODE] Commands are queued by `CommandList::Add(list, out, cmd, done, progress)`; an `Apply` function runs them on the simulation thread; `CommandList::Swap` is the swap; the loop calls the "pre-iteration function" once per iteration just before walking the command vector (native/mpfever_native.cpp:302-312,634,655-657; tools/targets_40420.txt:11-20). Relevance L (addresses in Appendix); concept M.
- [CODE] UI tools that issue a native construction (Bulldozer, ConstructionBuilder, LaneModifier x3 sites, ModuleBuilder, StreetBuilder, StreetTerminalBuilder for stops/signals/waypoints, TrackModifier, entity-window built-ins) all queue a `make_cmd BuildProposal` through `CommandList::Add` (native/mpfever_native.cpp:314-338). Relevance M. Home: engine.md (list of native construction tools). NEW.
- [CODE] The terrain tool (`UI::TerrainModifier`; a nearby tool at 0x549bea in 40408) is NOT holdable: it reads back the handle of its command, which a held command leaves empty; holding it crashed the game in `UI::TerrainModifier` (build 40408 comment; RESEARCH.md:107, "that crashed in 0.2.8"). Relevance M. Home: engine.md (terrain tool). NEW.
- [OBSERVED/CODE] Context flags of a WorldBuildProposal (read at payload offsets +0x358, +0x360, +0x362, +0x3d1, +0x3d2; "found by comparing commands that differ by one flag"): gatherBuildings, terrainAlignment, cleanupStreetGraph, ignoreErrors, playerInitiated; the context's player entity is at +0x36c; the command payload is at least 0x9c0 bytes (native/mpfever_native.cpp:1430-1434,1459-1475; RESEARCH.md:132 "gatherBuildings +0x358, terrain alignment +0x360, cleanup +0x362" for the Bulldozer settings). Relevance M. Home: api_catalog.md (Context fields of build proposals). NEW.
- [CODE] Command audit idea: counting applied commands per kind (128 kinds max) per game exposes unreplicated actions; written to the log every 10 s (native/mpfever_native.cpp:872-874,3220+). Relevance L.
- [CODE] The engine checks money for a build against the company in the build's context (not the savegame's): "a player could not build when the host was out of money" when the simulation read the wrong company (native/mpfever_native.cpp:431-433). Relevance M. Home: mechanics.md (construction payer) / engine.md. NEW.

Relevance H for a collector (reads from the interface copy are a snapshot lagging the simulation). Home: engine.md. NEW.
- [CODE] A new game state seen for the first time = a game just loaded; after load or resync the old entity ids "mean nothing" (native/mpfever_native.cpp:667-669,1301-1304). Relevance M: entity ids are only valid within one loaded game. CONFIRMS-EXISTING snapshot_schema.md header "IDs identify game entities while they exist". Home: engine.md.
- [CODE] "More than one game-state object calls Apply (two were seen next to each other at the start of a game)" (native/mpfever_native.cpp:1301). Relevance L.
- [OBSERVED/BUG] A 16-entry table of known states always replaced entry 0 once full: after 8 loads the two states of one game evicted each other. Fix: fill in turn (RESEARCH.md:136; native/mpfever_native.cpp:679). Relevance L (loading a save repeatedly creates new state objects; 2 per game).

Relevance M: a per-account "positions" list (money floating over buildings) exists on ACCOUNT components and is only drained for the local player. ## 6. ECS: add/remove ordering and id reuse

- [CODE] All world data lives in an entity-component system; `ecs::Engine::AddEntity` and `RemoveEntity` (RVAs in Appendix) (RESEARCH.md:41-42). Relevance M. Home: engine.md (ECS model); api_catalog.md. CONFIRMS-EXISTING partially: mechanics.md M9 and snapshot_schema.md refer to components (LOG_BOOK, ACCOUNT, LINE...) without describing the ECS.
- [CODE] Freed entity ids are reused first-in first-out (a deque at engine+0xd8..0xf8); otherwise a new id equals the size of the entity table (RESEARCH.md:43; native/mpfever_native.cpp:877-878: "hands out the numbers of removed entities again, oldest first"). Relevance H for the analyst: entity ids are RECYCLED. A vehicle id or line id seen in an old snapshot may later refer to a different entity. NEW. CONTRADICTS (soft) snapshot_schema.md "IDs identify game entities while they exist" only if read as stable forever; consistent with it. Recommend: history keyed by id must also store a creation marker. Home: engine.md + snapshot_schema.md warning; strategy for history joins.
- [CODE] During play every add and every remove happens on the simulation thread; ids stay identical across games only if the order of adds/removes is identical (RESEARCH.md:44). Instrumentation counts additions per [engine slot][thread kind] (interface/simulation/other) and logs the first off-simulation-thread additions in the simulation's engine with their caller (native/mpfever_native.cpp:877-912). [ASSUMED] that interface-thread adds are the "tool preview" entities in separate engines. Relevance M.
- [OBSERVED] In the "Test Multi 3" save, 5400 steps contained "all 116 714 entity adds and removes in the same order" on both games after the fix (RESEARCH.md:91). Relevance L: scale: ~116k add/remove events in 18 min of game time. Home: engine.md (scale).
- [CODE] Entity-change recording: "<iteration> <+|-><entity> <caller>" in entseq.txt (native/mpfever_native.cpp:2428). Relevance L.
- [CODE] Order fixes use the fact that the engine's freed ids join the FIFO queue per "modification" in an order that is "the engine's history, not the world's state"; the fix sorts a modification's freed ids in entity order before they join the queue (native/mpfever_native.cpp:2475-2515: order fix 0 "freed ids"). Relevance L. [CODE]. Home: engine.md (determinism).
- [CODE] Six simulation batches whose order is the engine's history and are sorted by entity id by the order fixes: (0) freed ids; (1) vehicles that want track, before the engine's SEEDED SHUFFLE and PRIORITY SORT decide who reserves first (entries {int node index, float}); (2) PersonCapacity candidates before their capacities are summed for one draw (a random draw is used to place persons); (3) persons and cargo leaving buildings (two vectors); (4) persons arriving on foot (before their stay draws); (5) vehicles at a line stop (the vector returned by the getter, before boarding loop) (native/mpfever_native.cpp:2475-2547,2515-2545). Ported from TPF3-MP (MIT, Juliansgith) and TPF2-MP (silver2127) (native/mpfever_native.cpp:2476-2478). Tag [CODE]; the claim that a given order "changes what the simulation decides" is the author's [CLAIM] without a test table. Home: mechanics.md (new M-section "Randomness and ordering in the simulation"), engine.md.
- [CLAIM] These sorts "change what the simulation decides" and so every game of a session must run them (native/mpfever_native.cpp:2480-2481); a vanilla single-player game uses the engine's unsorted order. Relevance M: single-player results contain an order-dependent random component. Home: strategy.md caveat on noisy measurements.
- [CODE] Engine datatype: `std::vector<Entity>` of i32 entity ids; record stride for the land-vehicle reservation records is 20 bytes (native/mpfever_native.cpp:2503-2545). Relevance L.

## 7. Lua runtime and the hash seed

- [CODE] Game scripts (towns, industries, construction scripts, game mechanics) run in Lua 5.2.2, inside the simulation, on the simulation thread (RESEARCH.md:58-59). Relevance H (version determines available language features for any mod-side Lua: no integer subtype, `goto` exists in 5.2, `bit32` exists, `table.unpack`, no `//`). Home: engine.md + api_catalog.md. NEW. CONTRADICTS nothing existing; note `.tl` files are Teal compiled to Lua (mechanics.md header "TEAL").
- [CODE] `lua_newstate` calls `makeseed` which mixes `_time64()` with a few memory addresses; the seed is stored in `g->seed` and used to hash every string; therefore `pairs()` order over tables with string keys differs per process and per launch (RESEARCH.md:66-70; native/mpfever_native.cpp:3182-3186). `makeseed` has one caller, `lua_newstate` (native/mpfever_native.cpp:3186). Relevance H: any collector that iterates string-keyed Lua tables with `pairs()` gets a nondeterministic order across launches; sort keys before output. Home: engine.md, snapshot_schema.md (ordering note), api_catalog.md. NEW.
- [OBSERVED] Fixing the seed (replace `makeseed` by `mov eax,'MPFV'; ret`) removed the dominant desync: before, 32-part hash differed after 1600-1900 steps and the full census after 100-400 steps; after, identical for 5400 steps, 3 runs of 3, and the "towns grow differently" report disappeared (RESEARCH.md:81,87-93). Relevance M. Home: engine.md (determinism evidence table, see section 13).
- [CODE] Consequences of unseeded iteration order claimed by the author: (1) towns pick different buildings to grow/upgrade/remove; (2) a new industry's internal lanes are numbered differently; (3) entity ids are reused in a different order; (4) people, cars, cargo, pollution, happiness and money diverge (RESEARCH.md:74-77; native/mpfever_native.cpp:3184-3185). Tag: causal chain [ASSUMED] (supported by the before/after table but not isolated per step). Relevance H: town growth building choice and industry lane numbering depend on Lua table order => even in vanilla single player, two identical saves with identical inputs will NOT give identical town growth. Home: mechanics.md M2 (town growth is non-reproducible), strategy.md.
- [CODE] The game's gui scripts: `base/init.lua` `require` pushes the file path on `_ug_filePathRequireStack` before loading and pops it only when the file ran to its end; the main menu UI runs in its own Lua state; mods are mounted only in a game; the main menu script is `gui/menu/main_menu.tl` and the pause menu `gui/main/pause_menu.tl` (in a game's UI state); `lua_load` can be wrapped; precompiled chunks start with byte 0x1B (native/mpfever_native.cpp:3122-3148). Relevance M. Home: api_catalog.md / engine.md (GUI Lua states). NEW.
- [CODE] Game script updates run on a thread pool: with fewer than 8 hardware threads the script update gets its own pool of max(1, threads/2) workers; with 8 or more it shares the general pool (in an order depending on thread timing) (native/mpfever_native.cpp:3097-3115). Relevance M: game scripts (towns, loans, industries) are updated in parallel in the vanilla game on >= 8 threads. [CODE]. Home: engine.md.
- [CODE] The engine's TWO other pools are sized round(0.55 x cores + 0.75) by static initialisers (build 40420 globals 0x4054fa8/0x4054fa4) (native/mpfever_native.cpp:3065-3067). Relevance L. Home: engine.md appendix.
- [CODE] Some simulation systems (traffic, persons) hand their work to the thread pool, sized from the processor count (via `_Thrd_hardware_concurrency` of msvcp140 and `GetSystemInfo` imports) (native/mpfever_native.cpp:1583-1586,3002-3005). Relevance L.
- [CODE] The Lua `string` hash seed in other Lua states (menu) is irrelevant for the world. Relevance L.
