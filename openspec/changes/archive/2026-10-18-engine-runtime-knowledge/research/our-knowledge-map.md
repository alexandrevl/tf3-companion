### 1.6 Conventions summary
- Source tags (`WIKI:`, `GM:`, `ECO:`, `SCR:`, `BASE:`, `TEAL:`, `CARGO:`, `IND:`) are used only in `mechanics.md` and `cargo_economy.md`.
- Evidence tags:
  - `[INFERENCE]`, `[UNVERIFIED]`, `[DISCREPANCY]`: mechanics and cargo_economy.
  - `[V]/[I]/[?]`: strategy only.
  - `[INFERENCE]`: also snapshot_schema.
- Rule (openspec change `rebrand-tf3-companion/specs/knowledge-base/spec.md:10`): every game-mechanic claim cites its source (official wiki page or game file path) or is marked `[INFERENCE]`/`[UNVERIFIED]`, and no verbatim game source is allowed in topics.
- There is no existing tag for "author of another mod claims it" (the dossier's [OBSERVED]/[CODE]/[ASSUMED]/[CLAIM]). A new source legend would be needed, for example a `MPF:` prefix. The existing legends define no such prefix.
- All knowledge text must be English (`openspec/specs/contributor-conventions/spec.md`; `AGENTS.md`).

## 2. How topics are discovered and served

- Discovery: `Companion.knowledge(topic=None)` in `src/tf3companion/service.py:401-410`.
  - It iterates `files("tf3companion").joinpath("knowledge").iterdir()` and keeps entries whose name ends in `.md`. The topic name is the entry name minus 3 characters.
  - No registry or whitelist. A new `.md` file in that directory is picked up automatically as topic `<stem>`.
  - No subdirectory recursion, so topics must be flat files.
  - Naming rule: whatever the stem is. Current stems mix underscores (`cargo_economy`, `snapshot_schema`) and a hyphen (`methodology-fields`).
  - Without a topic it returns `{"topics": sorted(names)}`. With an unknown topic it raises `LookupError("Topic '<t>' does not exist. Available: [...]")`. It returns `{"topic", "content"}` (full file text, UTF-8) otherwise.
  - Works offline with no game or store (`service.py:403`).
- MCP tool: `knowledge(topic: str | None)` at `src/tf3companion/mcp_server.py:153-155`, a pass-through. The description text is "Read packaged game knowledge; without a topic, list available topics." (also quoted in the tool list).
- CLI: `tf3c knowledge [topic]` (`src/tf3companion/cli.py:95-96`).
- MCP resources (`src/tf3companion/agent_experience.py`):
  - `tf3c://knowledge` (lines 204-212): the index builds `- [topic](tf3c://knowledge/topic): <summary>` per topic, with the summary taken as described in section 1.
  - `tf3c://knowledge/{topic}` (lines 214-221): validates membership first (a path-traversal guard, test `tests/test_store.py:167-171` uses `../notes`), then returns the content.
- Doctor check (`src/tf3companion/setup_tools.py:142-144`): the "knowledge" check only requires the directory to exist and contain at least one `.md`. It pins no names or counts.
- Packaging (`pyproject.toml:22-26`):
  - hatchling with `packages = ["src/tf3companion"]`. Every file under the package, including `knowledge/*.md`, is shipped. No explicit include list for knowledge.
  - The `[tool.hatch.build.targets.wheel.force-include]` entry exists only for the bridge mod (`mod/tf3_companion_bridge` → `tf3companion/_mod/tf3_companion_bridge`).
  - So a new topic file or a subdirectory needs no pyproject change. Files must stay inside the `tf3companion` package tree.
- Tests that touch knowledge:
  - `tests/test_methodology_packaging.py:34` asserts the built wheel contains `tf3companion/knowledge/methodology-fields.md` (it pins only this one name; it does not check the other four or the count).
  - `tests/test_setup.py:170` asserts the doctor "knowledge" check is `ok`.
  - `tests/test_methodology_mcp.py:21` lists tool names including `knowledge` (not topic names).
  - `tests/test_store.py:167-171` checks that `knowledge("../notes")` raises `LookupError`.
  - A methodology-docs test (there is a `tests/__pycache__/test_methodology_docs...pyc`) checks that `methodology-fields.md` is current.
  - No test pins the topic list, the count, or the names `mechanics`/`strategy`/`cargo_economy`/`snapshot_schema`.

## 5. Places where our files assume things MPFever research might contradict

- **Entity ids are stable while the entity exists.** `snapshot_schema.md:3` ("IDs identify game entities while they exist"). `store.py:33-41` keys `line_history` on `(game_time, line_id)`; `Store.line_history(line_id)` at `store.py:329-335` filters by `line_id`. `analysis` and `report_*` modules use line id as the continuity key.
  - Decisions store entities as strings or `{kind,id,name}` and resolve by id, then exact name, then partial name (`basic-reports/design.md:70`, `analysis-insights/design.md:74`, `analysis-insights/tasks.md:44` task 9.1).
  - The agent instructions say "use full entity names, not ids alone" (`agent_instructions.md:~11`, step 2).
  - `retire-local-analysis-generator/design.md:38` mentions "physical-vehicle history identity safety".
  - Risk: if MPFever shows entity ids are reused after demolition or save/load, or are not the same across clients or saves, the `line_history` key and the id-based decision references are exposed.
- **Tick and time units.**
  - `meta.yearDuration` = `api.util.getDefaultYearDuration()` is called "nominal financial/query-duration ticks" (`snapshot_schema.md:3`, `mechanics.md:24-25`, `snapshot.py:101-102`, `bridge.script.lua:506`). The collector uses it for the 1/12-year snapshot cadence (`bridge.script.lua:~775`) and for the profit window `fromTime = now - yearDuration`.
  - It is NOT assumed equal to the calendar year. Code that still divides ticks by `yearDuration`:
    - `report_bottlenecks.py:83` (spacing `year_duration/48`)
    - `report_history.py:394-401` (diagnostic "implied by meta.yearDuration", described as not a conversion rate)
    - `reports.py:635` (nominal elapsed years for a diagnostic)
  - `mechanics.md:24-27` and `docs/reports.md:87-94` declare raw tick, raw depot/terminal day-counter units and model lifespan unit as unverified. `report_policy.py:35` names `daysAtTerminal` "(unit unverified)". `long_wait_days` limit 36500.
  - `mechanics.md:234` assumes lifespan unit = days from 36525 = 100×365.25 ([INFERENCE]); `strategy.md:110` repeats it. Any MPFever fact on ticks per day, a 4 s day vs `millisPerDay` 2000 (`mechanics.md:308`), lifespan units, or `purchaseTime` units would confirm or contradict these.
  - `mechanics.md:104` (`growthPerTick` zero) and `cargo_economy.md:123` (rule `duration` 365/n; unit unverified) also assume unit semantics.
  - `game_time.py` interpolates purchase ticks between dated anchors (`game-calendar-v1`); it does not rely on a tick/day constant.
- **`profitYear` is a rolling window.** Described in `snapshot_schema.md:26`, `methodology-fields` INTRO, and `docs/reports.md:66-76`. The window is nominal `yearDuration` ticks (`bridge.script.lua:~ctx.fromTime`). If MPFever shows that `calculateBalance` windows or the `getLogValuePerYear` window behave differently, `snapshot_schema.md:26-27` and `mechanics.md` M9 (lines 288-304) are affected.
- **Load is instantaneous.** `snapshot_schema.md:30` (`capacity[]` is "occupancy at that instant"); `agent_instructions.md` Data caveats.
- **Save identity.** `docs/troubleshooting.md:61-70` and `agent_instructions.md` ("one companion store; no guaranteed save isolation"). `analysis-methodologies` and the `cross-platform-and-saves` change plan `meta.saveId`. Any MPFever knowledge of save identity or lineage conflicts with the "legacy history does not prove save isolation" stance (`mechanics.md:22-23`).
- **File locations and formats.** `snapshot_schema.md:3` and `docs/troubleshooting.md:19-45` assume the userdata location, the `towns_industries/` directory, and that the map-editor export directory is accepted by `app.saveUserdata` (comment in `bridge.script.lua:~725`). MPFever facts on userdata paths, language or build numbers would extend `troubleshooting.md` and `docs/install-mod.md`.
- **Stock ids.** `bridge.script.lua:~513` comment and `snapshot_schema.md:53`: stock ids are 0-based; `loadConfig`/capacity index = cargoTypeId + 1 (`snapshot_schema.md:50`, `report_towns.py:29`). Easy to contradict if MPFever shows different base indexing in other APIs.
- **Player scope.** `snapshot_schema.md:32,36,54` ("player's vehicles only", "only station groups used by the player's lines", "player's vehicle depots only"). The mod handles one human player; there is no multi-company model in the knowledge. Any MPFever multi-company/ownership facts are NEW material for `snapshot_schema.md` (`player` filter via `PLAYER_OWNED`) and for an engine/ownership topic.
- **Schema version.** `snapshot_schema.md:5-7` (reader accepts 1-3) versus `bridge.script.lua:17` (emits 1) versus the `cross-platform-and-saves` plan (schema 2) and `service-boundary-hardening` (revision 2): internal inconsistency to be aware of when documenting new fields.
