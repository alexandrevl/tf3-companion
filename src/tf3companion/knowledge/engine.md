# Transport Fever 3 engine and runtime behaviour

How the game engine runs time, threads, Lua states, entities, commands, construction and files, as far as a read-only collector and analyst need to know it; every imported fact is labelled with its evidence class.

> **Evidence legend (imported research).** `MPF:<file>` cites a file of MPFever (https://github.com/dkdknight/MPFever, MIT, studied at commit `ae5fc96`; paths relative to its repository root). `[ADOPTED: observed|code|assumed|claim]` marks a fact taken on the MPFever author's word and not verified by this project; the class is the author's own: observed = measured by the author, code = read by the author in game code or the engine, assumed = the author's assumption, claim = stated without evidence. Every statement is paraphrased. `[INFERENCE]`, `[UNVERIFIED]` and `[DISCREPANCY]` keep their existing meaning.

Cross-references: `mechanics.md` (game rules M1 to M12; "Time units used by the companion" owns calendar accounting), `snapshot_schema.md` (what the collector writes). Nothing here changes those rules. This topic describes behaviour; it is not a procedure for altering, commanding or hooking the game, and the collector stays read-only.

## Studied builds

- Two builds of the game executable were studied by MPFever: **40408** and **40420**. The "build number" is a label the author attached to the link timestamp stored in the executable's header; the launcher reads that timestamp, and an unknown stamp is reported as "unknown build". No file-version or product-version resource is read anywhere. [ADOPTED: code] (MPF:native/mpfever_native.cpp:20,350-351; MPF:launcher/Reporter.cs:121-138)
- Build scope of the evidence: the engine notes were studied on **40420** unless a statement names 40408. [ADOPTED: claim] (MPF:docs/RESEARCH.md:5)
- The author's changelog says the game moved from 40408 to 40420 in MPFever 0.2.9. [ADOPTED: observed] (MPF:docs/CHANGELOG.txt:571-577) [INFERENCE] So changelog observations from 0.2.9 onward (0.2.10 to 0.3.15) were made on 40420, and those up to 0.2.8 on 40408. This topic writes "(build 40420)" or "(build 40408)" next to a measurement on that basis; the changelog does not attribute each entry itself.
- Internal engine addresses change with every update; the author checks bytes before relying on them, and between the two builds the same functions were found again at shifted places. Internal structure layouts (field positions) were still those of 40420 on later builds. The Lua API is the stable surface; engine internals are not. [ADOPTED: claim] (MPF:docs/RESEARCH.md:5) [ADOPTED: code] (MPF:native/mpfever_native.cpp:314-338; MPF:docs/CHANGELOG.txt:62-67)
- The game is a 64-bit Windows program built with the MSVC toolchain, and it loads a same-named library from its own folder first (Windows search order). All of MPFever's evidence comes from Windows. [ADOPTED: code] (MPF:native/mpfever_native.cpp:560,1587,2019; MPF:native/winhttp_proxy.cpp:1-6,38-51)
- Our collector exports `meta.buildVersion` from the game's global `getBuildVersion` (`mod/tf3_companion_bridge/content/tf3_companion/bridge.script.lua:183`). The game's definitions declare it as a global that returns a string (`TEAL:util.d.tl:206`, `TEAL:main.d.tl:39`), which agrees with MPFever's tests mocking it as a plain string. The install read for task 8.2 is the macOS Steam copy (a Mach-O executable, with the strings "steam", "64-bit" and "Mac Appstore" beside the label): it embeds the Lua template of `getBuildVersion` and the label **40420**, and the label 40408 does not occur in it; the Steam manifest of that install records build id 25754343, last updated 2026-10-08. The platform differs from MPFever's Windows copy, so the Windows-only statements of this topic stay the author's. Whether the run-time return value equals 40420 is still [UNVERIFIED] (see Known unknowns).
- Addresses, offsets, hook sites, patch techniques and diagnostic switches found in the research are deliberately left out of this topic (design decision 5 and 7 of the change).

## E1 - Clock, steps and speed

**Step and handshake**
- The simulation advances in **steps** of 200 game-time units. The game script `update` is called once per step, and the author states the step as 200 ms of game time. [ADOPTED: code] (MPF:mod/mpfever_1/content/mpfever_bridge.script.lua:6,28; MPF:docs/RESEARCH.md:32)
- The simulation thread runs one loop iteration per step and applies queued commands before each step. [ADOPTED: code] (MPF:docs/RESEARCH.md:32; MPF:native/mpfever_native.cpp:582-583,656-657)
- The main (interface) thread runs a synchronisation call every 200 ms regardless of game speed; it swaps the command list, so commands added by the interface reach the simulation only at that swap. [ADOPTED: code] (MPF:docs/RESEARCH.md:31)
- Each synchronisation hands the simulation thread its next batch of steps: one step at x1, four at x4 (speeds exist as x1, x2, x4), and the renderer interpolates across the batch. A scale factor on the batch interval slows real time without changing game time or step results. [ADOPTED: code] (MPF:native/mpfever_native.cpp:2828-2831; MPF:docs/CHANGELOG.txt:52-58)
- [DISCREPANCY] Sync interval. Version A: exactly every 200 ms (MPF:docs/RESEARCH.md:31). Version B: every `guiFrameTime`, an interval the engine estimates itself at 200 to 400 ms (MPF:native/mpfever_native.cpp:2828-2831). Both are the author's reading of build 40420; this project has not chosen. The plausible-value window of that field in the native code is 20 ms to 2 s, and its unit (microseconds) is the author's assumption. [ADOPTED: assumed] (MPF:native/mpfever_native.cpp:2828-2888)
- A scale of 5400 steps is 18 minutes of game time (5400 x 200 ms = 1080 s); in that run about 116 thousand entity adds and removes occurred (build 40420, a multiplayer test save). [ADOPTED: observed] (MPF:docs/RESEARCH.md:91)

**Simulation time is step-driven, not wall-driven**
- Pausing the simulation for 60 s of real time between steps changed nothing in the simulation. [ADOPTED: observed] (MPF:docs/RESEARCH.md:97)
- With a stopped simulation the interface sees no clock movement for about 0.45 s of real time; a clock that stays still for 12 interface frames proves nothing, because the interface sees the simulation clock only at the 200 ms handshake. [ADOPTED: observed] (MPF:docs/RESEARCH.md:109)
- From the interface Lua state, the clock and the step counter change only when the interface takes over a new copy of simulation state, about five times a second while the game stands still; the clock and the step counter always changed together, and the speed value changed only with a new copy (build 40420, autotests at x1, x2, x4). [ADOPTED: observed] (MPF:mod/mpfever_1/content/mpfever_bridge.script.lua:3717-3722)
- Reading game data faster than the handshake returns a stale copy. [INFERENCE] from the two entries above and the two-copy model in E2.

**Speed and pause**
- The world's speed component field `speedup` is the engine's own speed (0 = stopped); it is not the session speed the interface buttons show. It can read 0 while the simulation thread is still finishing steps it had started, so speed 0 alone does not prove the world is still; the engine's own update counter not moving is the author's test of stillness. [ADOPTED: code] (MPF:mod/mpfever_1/content/mpfever_bridge.script.lua:36-41,3690-3692,3707; MPF:docs/CHANGELOG.txt:198-201) The definitions describe the field as a non-negative multiplier with 0 meaning paused (`TEAL:engine.d.tl:415-422`), and the game's own interface lowers it below the chosen speed when the estimated maximum game speed is smaller (value 3 stands for a chosen 4 throttled by 1; `gui/main/game.tl:616-668` in `gui.zip`), so the field is not always the speed of the button.
- In MPFever's lockstep runtime the engine holds speed at 0 between batches, so the speed the interface reads is not the player-chosen speed there; in a normal game the buttons follow the engine. [ADOPTED: observed] (MPF:docs/CHANGELOG.txt:296-299)
- A game running at speed N runs several steps per frame and a speed change takes a frame; at x4 a game can pass a point it was meant to stop at by a few steps. [ADOPTED: assumed] (MPF:mod/mpfever_1/content/mpfever_bridge.script.lua:2094-2097,3838-3841) [ADOPTED: observed] (MPF:docs/CHANGELOG.txt:704-707)
- A game that is paused still runs its scripts; time does not advance. [ADOPTED: code] (MPF:docs/CHANGELOG.txt:198-201)

**The simulation script is not once per step**
- The game-script `update` also runs while game time stands still (a held build, a synchronisation barrier, a held terrain tool). It is called per call, not once per distinct game time; anything done "once per call" is not once per step, and periodic work keyed to a game-time counter is the only reliable base. [ADOPTED: observed] (MPF:docs/CHANGELOG.txt:216-224; MPF:mod/mpfever_1/content/mpfever_bridge.script.lua:920-923,1019-1024)
- The extra `dt` argument of `update` is passed by the engine. The industry script multiplies it by 1000 before relating it to the year duration (`GM:industries/industries.script.tl:55,128`), which reads `dt` as seconds against a year measured in milliseconds [INFERENCE]; a 200-unit step would then be `dt` = 0.2, but no script states the step size, so the 200 of the step entries stays the author's figure. The author does not state the unit. [UNVERIFIED] (MPF:mod/mpfever_1/content/mpfever_bridge.script.lua:1250,1303)

**Counters of the game-time component**
- The world entity's `GAME_TIME` component carries `gameTime` (the current ingame time), `gameTime0` (the time of the last update), `dates`, `timeOfDaySec`, `updateCount` and `tickCount` (`TEAL:engine.d.tl:425-439`). Our collector reads `gameTime` of that component (`bridge.script.lua:505`). The game compares `gameTime` with `getDefaultYearDuration() / 2` and with default month durations in its loan script, so they are one unit (`GM:finance/loan.script.tl:61,150`).
- `updateCount` counts simulation updates and does not tick while the simulation is paused (`TEAL:engine.d.tl:436-437`). That it is one per simulation step and identical on every machine for the same save and inputs is the author's reading. [ADOPTED: code] (MPF:mod/mpfever_1/content/mpfever_bridge.script.lua:3713; MPF:native/mpfever_native.cpp:2597-2630)
- `tickCount` counts simulation ticks, once per frame, and also ticks while the game is paused (`TEAL:engine.d.tl:434-435`), so it is not a step count. That it differs between machines is the author's reading. [ADOPTED: code] (MPF:mod/mpfever_1/content/mpfever_bridge.script.lua:3712-3713,4073-4075; MPF:docs/RESEARCH.md:192; MPF:docs/CHANGELOG.txt:95-99)
- [DISCREPANCY] Does the simulation read `tickCount`? Version A: it "does not seem to" use it, not yet proven (MPF:docs/RESEARCH.md:192,215). Version B: seven simulation call sites read it, to seed the land-vehicle shuffle, the vehicle variant pick, and town and street development (MPF:native/mpfever_native.cpp:2607-2611; MPF:docs/CHANGELOG.txt:95-99). Version B is code evidence for build 40420; version A is the earlier note. If B holds, town growth and vehicle choice depend on a frame counter.
- **Which counter our snapshots export is [UNVERIFIED]**: the collector writes `gameTime`; whether `gameTime` advances with `updateCount` (200 per step), whether `meta.gameTime` is a step-based or a frame-based value, and whether it moves while paused have not been checked by this project. Do not equate a raw tick with simulated steps; calendar conversion stays under the existing `mechanics.md` "Time units" rules.

**Game day**
- [DISCREPANCY] Length of a game day at x1. Version A: 4 s, i.e. 4000 ms (`mechanics.md` M10, WIKI:simulation:overview). Version B: `ECO:cargotype.script.lua` assumes a `millisPerDay` of 2000 (flagged `[UNVERIFIED]` in M10). Version C (MPFever): an empty station group expires 20 game days later, seen as about 80 s at x1, which fits 4000 ms per day (build 40420, MPFever 0.3.14). [ADOPTED: observed] (MPF:docs/CHANGELOG.txt:114-116) C supports A but does not exclude a configuration value of 2000 elsewhere; no choice is made here.
- [INFERENCE] If a day is 4 s at x1 and a step is 200 ms of game time, a day is 20 steps at x1; the research never states this and the unit of a "step" against `gameTime` ticks is unverified.
- Game scripts read for task 8.2 (build 40420 scripts) settle neither version: no script holds a numeric day, month or year length. The day, month and year come from `api.util.getDefaultDayDuration`, `getDefaultMonthDuration` and `getDefaultYearDuration` ("game ticks", `TEAL:util.d.tl:110-120`) and the live `GAME_SPEED.millisPerDay`, and the 2000 of version B is a local constant of the economy script used only for its price curves (`ECO:cargotype.script.lua:3-47`). The game bar defines the calendar-speed factor as `getDefaultDayDuration() / millisPerDay`, so factor 1 means `millisPerDay` equal to the default day (`gui/game_bar/game_bar_widgets.tl:321-351` in `gui.zip`); the constant itself is returned by the engine. [UNVERIFIED] The default day in game-time units. Check: read `api.util.getDefaultDayDuration()` in a throwaway script.

## E2 - Threads, Lua states and game-state copies

**Threads**
- The game runs an interface (main) thread, a simulation thread and further worker threads. The game is loaded in-process on its main thread. [ADOPTED: code] (MPF:native/mpfever_native.cpp:3214; MPF:docs/CHANGELOG.txt:422-427)
- All game scripts (towns, industries, construction scripts, game mechanics) run in Lua 5.2.2 inside the simulation. [ADOPTED: code] (MPF:docs/RESEARCH.md:58-59)
- During play every entity add and remove happens on the simulation thread. [ADOPTED: code] (MPF:docs/RESEARCH.md:44) Some simulation systems (traffic, persons) hand work to a thread pool sized from the processor count, and the engine has two further pools sized by the formula round(0.55 x cores + 0.75). [ADOPTED: code] (MPF:native/mpfever_native.cpp:1583-1586,3002-3005,3065-3067)
- Game-script updates run on a pool: on machines with fewer than 8 hardware threads the script update gets its own pool of max(1, threads/2) workers; with 8 or more it shares the general pool and the order of script updates then depends on thread timing (build 40420). [ADOPTED: code] (MPF:native/mpfever_native.cpp:3097-3115)
- [DISCREPANCY] Script-pool size on small machines. Version A: a single worker below 8 threads (MPF:docs/CHANGELOG.txt:697-703, observed in 0.1.1). Version B: max(1, threads/2) workers (MPF:native/mpfever_native.cpp:3097-3115, code). Both agree that 8 or more threads update scripts in parallel in timing-dependent order.
- Processor count and thread scheduling had no effect on the simulation once the Lua hash seed was fixed (E4). [ADOPTED: observed] (MPF:docs/RESEARCH.md:98)

**Two game-state copies**
- The engine keeps **two game-state objects** and copies one into the other at every iteration; the interface reads one while the simulation writes the other. A read from the interface is therefore a snapshot that lags the simulation. [ADOPTED: code] (MPF:docs/RESEARCH.md:40; MPF:native/mpfever_native.cpp:602-603,1301-1304)
- A game state seen for the first time means a game has just been loaded; after a load the old entity ids mean nothing (E3). Loading a save repeatedly creates new state objects, two per game. [ADOPTED: code] (MPF:native/mpfever_native.cpp:667-669,1301-1304) [ADOPTED: observed] (MPF:docs/RESEARCH.md:136)
- Writing into a game state that has been freed (unloaded) crashes the game; writes belong only to the live simulation. [ADOPTED: observed] (MPF:docs/CHANGELOG.txt:416-419)
- The interface reading data heavily (a full census of components) did not change the simulation once the seed was fixed: reading from the interface does not perturb the simulation. This supports the read-only collector design. [ADOPTED: observed] (MPF:docs/RESEARCH.md:99)

**Lua states**
- The game runs several separate Lua states: (1) the interface (UI) state, with windows and tools; (2) the GUI half of a game script (`guiUpdate`) and (3) the simulation half of the same script (`update`); (4) the main-menu UI state, in which mods are not loaded and which is mounted only in a game for mods; (5) the application-script state (started by the `--script` command line), where the `app` table with save and load functions lives. [ADOPTED: code] (MPF:mod/mpfever_1/content/mpfever_ui.script.lua:1-8; MPF:mod/mpfever_1/content/mpfever_menu.lua:1-6; MPF:mod/mpfever_1/content/mpfever_auto.lua:1-5,27-135; MPF:mod/mpfever_1/content/mpfever_pause.lua:1-6)
- Data passes between states only through files or through module tables that stay shared inside one state (also across a savegame reload); module tables are per state, so wrapping a function once affects every caller in that state. [ADOPTED: code] (MPF:mod/mpfever_1/content/mpfever_common.lua:157-160,1432-1440; MPF:mod/mpfever_1/content/mpfever_progression.lua:123-153)
- A game script is declared by a module that names its `update`, event handler, `guiUpdate` and GUI event handler functions as `file@function` strings; the simulation half receives `(params, state, dt)` and the engine event handler receives source, state, id, name and param; `state:get()`/`state:set()` hold the script's state, saved with the savegame. [ADOPTED: code] (MPF:mod/mpfever_1/content/mpfever.gs.lua:1-16; MPF:tests/test_lockstep.py:157-169; MPF:mod/mpfever_1/content/mpfever_bridge.script.lua:923-925,1068)
- `app.saveGame`, `app.SaveGameNamespace.getSavegame`, `app.findAllSavegames`, `app.loadGame` and `app.saveUserdata` are reachable only in some of these states. [ADOPTED: code] (MPF:mod/mpfever_1/content/mpfever_bridge.script.lua:4455-4495)
- **Our collector runs in the GUI half of its game script** (`guiUpdate`), checks that `app.saveUserdata` exists before writing, and writes snapshots only through `app.saveUserdata` (own source: `mod/tf3_companion_bridge/content/tf3_companion/bridge.script.lua:752-789`; snapshot_schema.md).
- `api.engine.util.getPlayer()` returns the entity of the company the interface plays; the game's own loan, company, ticket-price and notification scripts also ask `getPlayer()` and assume one company. In a single-company save that entity is the player's company. [ADOPTED: code] (MPF:mod/mpfever_1/content/mpfever_bridge.script.lua:523-527,729-731; MPF:mod/mpfever_1/content/mpfever_progression.lua:81-84)
- "Local player" is an interface concept stored once per game state, but 59 places in the executable (build 40420) read it, some on the simulation thread. When the simulation read another company there, a road vehicle of the saved company drove faster and the money followed, so simulation behaviour is not purely a function of the world. [ADOPTED: code] (MPF:docs/RESEARCH.md:48-50; MPF:native/mpfever_native.cpp:2189-2219,2270-2297) [ADOPTED: observed] (MPF:native/mpfever_native.cpp:1289-1291)
- The money-popup positions kept on each account are drained for the local player's account only, at the start and end of each simulation iteration; other companies' popup lists are not emptied. [ADOPTED: code] (MPF:native/mpfever_native.cpp:415-418,667-704,1331-1332,2950)
- The line viewers on the map draw "the lines of one player" from a per-player table and keep the player they were created with; in MPFever a client company's routes vanished from the map. Confirming in a real game was left open. [ADOPTED: code] (MPF:docs/RESEARCH.md:126; MPF:docs/CHANGELOG.txt:378-380) [ADOPTED: assumed] (MPF:docs/RESEARCH.md:124,220)
- The game's Teal sources (`.tl`) are compiled to Lua and loaded by the engine's chunk loader (the main-menu and pause-menu scripts are `.tl`); `::/...` names reach the base game's files and `<mod>_1::/...` names the mod's. [ADOPTED: code] (MPF:native/mpfever_native.cpp:3122-3136; MPF:docs/CHANGELOG.txt:150-151)
- The game's main menu is a React-like GUI written in Lua, and menu pages are extensible by mods. [ADOPTED: claim] (MPF:docs/CHANGELOG.txt:194-197)

## E3 - Entities and ids

- All world data lives in an **entity-component system (ECS)**: an entity is an id; its data are components looked up by type. A lookup of a component the entity does not have is an engine assertion in the component lookup, not an empty result (seen as a crash on selecting or demolishing a construction whose segments had been rebuilt, MPFever 0.3.15, build 40420). [ADOPTED: code] (MPF:docs/RESEARCH.md:41-42; MPF:docs/CHANGELOG.txt:26-33)
- **Id reuse caveat.** Freed entity ids are handed out again, first-in first-out (oldest freed first); otherwise a new id equals the size of the entity table. An id seen in an old snapshot can later name a different entity. [ADOPTED: code] (MPF:docs/RESEARCH.md:43; MPF:native/mpfever_native.cpp:877-878; MPF:docs/CHANGELOG.txt:93-96) Whether this reuse happens in a long single-player history is [UNVERIFIED] (see Known unknowns). Relating two snapshots through an id therefore also needs the entity's name or other descriptors.
- [DISCREPANCY] Are new ids increasing? Version A: ids are handed out first-in first-out from freed ids (MPF:docs/RESEARCH.md:43). Version B: the author's code finds a freshly created entity as the largest id not seen before, and a vehicle bought in one step gets consecutive ids (MPF:mod/mpfever_1/content/mpfever_bridge.script.lua:670-672,1030-1031; MPF:docs/CHANGELOG.txt:221-224), which only holds while no freed id is waiting. B is the author's assumption. [ADOPTED: assumed] (MPF:mod/mpfever_1/content/mpfever_bridge.script.lua:670-672)
- All entity kinds draw ids from one global counter, so one extra or missing entity of any kind shifts the numbering of everything created after it (vehicles, people, segments). [ADOPTED: observed] (MPF:mod/mpfever_1/content/mpfever_bridge.script.lua:13,1462-1464,4902; MPF:docs/CHANGELOG.txt:241-245)
- **Session-id caveat.** Ids that come from the savegame are identical everywhere. Ids allocated afterwards can differ between machines: the interface of one game allocates entities the others never see (tool previews, store windows), so every entity allocated later can get a different id. The author's test reproduces this (a vehicle bought in two games got different ids). [ADOPTED: observed] (MPF:mod/mpfever_1/content/mpfever_refs.lua:1-13; MPF:tests/test_lockstep.py:1-12,24,324) [ADOPTED: code] (MPF:mod/mpfever_1/content/mpfever_refs.lua:420-425)
- The same save loaded twice gives the same ids to existing entities; the ids of new segments and nodes depend on the exact history before the build. [ADOPTED: observed] (MPF:docs/CHANGELOG.txt:255-256)
- Ids from an old (unloaded) game state mean nothing in a newly loaded one; loading invalidates every cached id and handle, and a plain id can name another kind of entity after a reload (0.3.6, build 40420). [ADOPTED: observed] (MPF:docs/CHANGELOG.txt:86-88,350-352)
- Stable descriptors the author uses instead of ids: construction = file name plus position; depot or station = its construction plus index; road node = position (within 0.5 m); road edge = positions of its two end nodes; street-side stop = its edge plus side; station group = its first station; brush assets = first model id plus position. A vehicle or line created in the session has no stable descriptor. [ADOPTED: code] (MPF:mod/mpfever_1/content/mpfever_refs.lua:416-418,420-480,518-535)
- Entity ids in a build's proposal are placeholders (negative numbers) whose real ids differ between games. [ADOPTED: code] (MPF:mod/mpfever_1/content/mpfever_bridge.script.lua:2795,3007,4693)
- **Transient component reads.** A component read is valid only until the next read: its fields are copied at that moment. [ADOPTED: claim] (MPF:mod/mpfever_1/content/mpfever_bridge_second.lua:7836) Dangling ids are possible, and `api.engine.entityExists(entity)` exists to validate a stale id. [ADOPTED: code] (MPF:mod/mpfever_1/content/mpfever_bridge.script.lua:447-449)
- **Entities the UI allocates.** The interface allocates entities for tool previews and store windows; kind-52 preview commands are applied directly, outside the simulation loop (E5). Counting additions by thread kind, the author found the first off-simulation-thread additions in the simulation's engine and assumed them to be preview entities in separate engines. [ADOPTED: assumed] (MPF:native/mpfever_native.cpp:877-912; MPF:native/mpfever_native.cpp:1355,1368-1369)
- **Enumeration restrictions.** `forEachEntityWithComponent` lists entities with a component but "not every type can be listed": `BASE_EDGE` and `BASE_NODE` refuse with the error "Cannot loop over this component type", and the street graph is reached through the node-to-segment map instead. [ADOPTED: code] (MPF:mod/mpfever_1/content/mpfever_bridge.script.lua:4517-4525; MPF:mod/mpfever_1/content/mpfever_refs.lua:143-190)
- Scale: trees and pollution emitters together exceed 100 thousand entities on a map and carry nothing else; asking an entity for a component it does not have is slow; the full text of a `TRANSPORT_NETWORK` component takes about a quarter of a second, and a full dump of all of them took 26 minutes. [ADOPTED: claim] (MPF:mod/mpfever_1/content/mpfever_bridge.script.lua:4526,4528,4599-4606; MPF:docs/RESEARCH.md:147) Looking nodes and segments up by scanning was about 500 times slower than indexing once (MPFever 0.3.8, build 40420). [ADOPTED: observed] (MPF:docs/CHANGELOG.txt:300-303)
- Cost scale: hashing all edges and constructions held the simulation about 0.3 s every 10 s on large maps (build 40420). [ADOPTED: observed] (MPF:docs/CHANGELOG.txt:283-286) Dumping a very large build proposal took 4 to 74 s while the simulation stood still on a large map (build 40420). [ADOPTED: observed] (MPF:mod/mpfever_1/content/mpfever_bridge.script.lua:1662-1668)
- Entities of a modular station can number in the hundreds: a cargo station with 2 electrified tracks has 48 segments, and a station of 200 nodes was seen (build 40420). [ADOPTED: observed] (MPF:docs/CHANGELOG.txt:24-25,124-125)
- The simulated persons and cargo are individual entities (`SIM_PERSON*`, `SIM_CARGO`, `SIM_ENTITY_*`, with `MOVE_PATH` for movement) alongside the per-stock counts in `STOCK_LIST`; the component catalogue is in `api_catalog` ownership groups (E9). [ADOPTED: code] (MPF:docs/RESEARCH.md:168,184)
- **Savegame ids and sorting.** Entity ids are never compared across machines by the author, only counts and content; two machines can hold the same world with different numbering of later entities. [ADOPTED: code] (MPF:mod/mpfever_1/content/mpfever_bridge.script.lua:13,84-93,133-148)

## E4 - Lua runtime and sandbox

- **Version.** The game's Lua is **5.2.2** (build 40420); this follows from the version string and 32-bit formatting limits the author observed. [ADOPTED: observed] (MPF:docs/CHANGELOG.txt:401; MPF:docs/RESEARCH.md:58-59; MPF:mod/mpfever_1/content/mpfever_common.lua:92-94,125-137)
- **String-hash seed and iteration order.** When a Lua state is created, the engine's seed function mixes the clock with a few memory addresses; the seed hashes every string, so the traversal order of `pairs()` over a table with string keys **differs on every PC and every launch**. The game's own scripts walk such tables, so towns choose different buildings to grow, upgrade or remove, a new industry's lanes are numbered differently, and entity ids are reused in a different order. [ADOPTED: code] (MPF:docs/RESEARCH.md:66-77; MPF:native/mpfever_native.cpp:3182-3186) [ADOPTED: observed] (MPF:docs/CHANGELOG.txt:400-407)

- [INFERENCE] In vanilla single player (no fixed seed) two identical saves with identical inputs do not give identical town growth or industry lane numbering. Anything a collector exports in `pairs()` order is unordered between launches; ordering by id or name is the analyst's responsibility. The existence of this randomisation in vanilla is not tested by this project ([UNVERIFIED], see Known unknowns).
- **Unsaved random state.** The Lua random-number state is not part of the savegame and differs between games.
